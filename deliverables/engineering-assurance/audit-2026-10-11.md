### 本轮修复的具体语义

会话快照数据库主键使用“服务端 owner + 用户 session key”的确定性哈希命名空间。
payload 额外校验 owner_subject，内存 window 同样用属主键。
未标 owner 的旧快照不自动分配给首次访问者，防止历史数据被其他人认领；
这意味着旧快照需要经过明确属主核验后迁移，旧条目保留未删。

只导出/恢复自己的 DSL runs，恢复时阻止覆盖别人的 run_id，并保留 execution_id。
全局工具尚无 owner 存储，因此本轮用户快照明确不导出/恢复全局工具，
响应显示 global_registry_not_owner_scoped；不会把降级伪装成功能齐全。
恢复改为 POST；旧 GET 兼容入口也要求 CSRF。客户端以后应使用 POST。
分叉列表和时间线在 SQL 层按 owner 过滤，读、对比和弃用检查记录属主。

新发行校验器逐个散列包内所有文件（清单本身除外），覆盖 EXE、DLL、前端、脚本。
缺脚本、缺清单、空清单、错误路径、缺文件或哈希不符均拒绝启动。
使用 .NET SHA256，避免 Python 子进程环境里 Get-FileHash 模块不可见的问题。
哈希校验只证明与清单一致，包外签名和软件来源真实性仍需独立签名方案。

更新资产只能是单一 ZIP 文件名，pending ZIP 必须位于本安装目录，
目标路径不能经链接逃出安装根。stage/apply/rollback 拒绝 service 身份，
更新能力限制在本地运行面。未实现自动替换启动器，现有 apply 仅准备文件。

## 质量与应用价值评价

| 维度 | 判断 | 理由 |
|---|---|---|
| 工程质量 | 有基础，但可靠发布门禁尚未闭合 | 有迁移、测试、隔离、审计和恢复设计；新提交仍能让启动整体失效，测试大量依赖局部或替身 |
| 代码质量 | 中等、局部扎实，跨模块一致性不足 | 多服务与类型契约已成形；内存全局状态、两套执行面、漏接线和安全策略分散造成回归 |
| 架构质量 | 方向有价值，复杂度偏高 | 工作台、调度、权限、证据链值得保留；多个内核与全局单例让身份/成本/恢复难以统一 |
| 实用质量 | 技术用户受控试用可用；普通用户端到端尚不稳定 | 真实包能启动，部分流程有验证；“输入目标自动交付”仍缺统一、可信、可恢复的执行链 |
| 应用价值 | 本地多 Agent 管理与工程证据工作台有实际价值 | 能集中配置/路由/审查与结果追踪；价值应通过具体小任务成功率与节省时间度量 |
| 成本性价比 | 已有开发投入有复用价值，继续扩功能的边际收益暂低 | 当前成本主要在多执行面的联调、维护与误失败重试；先修核心闭环比继续堆展示模块更划算 |
| 生产成熟度 | 未达到可无条件公开部署/企业交付的证据门槛 | 剩余隔离、安全执行、费用与证据真值、全量验收、发行/升级签名均未关闭 |

成本与收益不要只按 token/s 或功能数量比较。应记录同一真实任务的完成率、
重试次数、耗时、模型实际账单、人工修正时间和维护成本。
本地运行不等于总成本为零；BSL 非商业使用允许范围也不等于企业内部生产免费。
