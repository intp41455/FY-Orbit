## 关键技术决策（踩坑记录，勿重犯）

### 1. FastAPI `_IncludedRouter` —— 路由探测不能用 `app.routes`
该版本把 `include_router` 的结果包在 `_IncludedRouter` 内，直接遍历 `app.routes` 只能看到 5 条顶层路由，会**误判路由没挂上**。正确做法：`app.openapi()["paths"]`。

### 2. SQLAlchemy JSON 列不追踪原地修改（血坑）
`_quest_dict()` 若返回 `row.quest_state` 的同一引用，调用方就地改 `q["care"]` 后，另一个用自己 `q` 整体回写的函数会把它覆盖掉 → 首次照料标记永远不落库（实测 `quest_state` 只有 `tutorial` 键）。
**修法**：`copy.deepcopy(raw)` 返回独立副本，调用方显式 `row.quest_state = q`。

### 3. `preference_view` 的 `recognized` 恒为 True
`get_save` 把归一化后的 `persona`（总落在 PREFERENCES 内）传给 `preference_view`，导致 `personality in PREFERENCES` 永远成立。
**修法**：传**原始** `personality`，并在 `preference_view` 内加 `isinstance(personality, str)` 校验。

### 4. 派生状态的记账顺序（t3/t5 修复）
`_sync_level` 原本在 action handler **之后**调用，导致 `claim` 读的是上一轮旧进度 → 新手链 t3（decorate）永远差一步。且 `decorate` 事件在全服务里**没有任何触发点**——W2 不拥有布置动作，家具件数只能从 W1 `CabinInterior` 表派生。
**修法**：`_sync_level` 提到 handler 之前；内部调 `_sync_decorate_progress`（按 `件数 − baseline_items` 绝对值回填，只增不减）；`_advance_quests(row,"level",new_level)` 同时补进 action 路径（原只在 `get_save` 里，纯动作流下 t5 卡死）。

### 5. 测试前提 ≠ 服务缺陷（省时经验）
「同一探险点连采 3 次」第 2、3 次必然 409（刷新窗口 2-4h，设计如此）——写「完成三次探险」类测试必须换 3 个不同点。
改 `daily_seed` 后 `_ensure_daily` 会重置为「今天」的同一 seed，故 ids 相同是设计而非 bug。

### 6. meta 契约必须带 `event`
`progress` 字典按**事件名**记账（explore/feed/decorate/level），所以 `meta.tutorial_steps` 必须下发 `event`，否则前端只能硬编码「t1 是 explore」= 把真源复制一份。已在 meta 补 `event` + `daily_pool.reward_label`，并加测试锁定。
